# cg-terminal Phase 2 reference implementation

Use Node 24 for collection and compilation. The existing provider client, encrypted response handling and feature calculations are TypeScript. Keep MT5 valuation, ticket reconciliation and the PIT-16 solver in Python. The reference package contains the WAL schema, a compiler/verifier, and the policy module that contains the eleven gates and shared-headroom calculator. Run it in shadow mode with a restricted report directory.

## 1. Collector cutover

1. Extract provider calls and normalization from CVD, book walls and liquidation levels into modules that take an explicit provider client and clock. Remove Next.js request/response imports from the extracted functions. Reuse the current `client.ts` parsing and circuit breaker, the book-wall scanner and the liquidation model. Bootstrap the standalone process through the existing TypeScript build toolchain so it resolves the same modules as Next. Its input is a typed instrument/window/venue set. Its output is normalized facts, complete coverage and provenance.
2. First feed the SQLite materializer by tapping the **current** fetch path. Shadow compilation reads that stream and costs zero additional upstream requests. Capture actual request weights, especially the venue fan-out for each 3D/7D/30D liquidation window. Then drain in-flight legacy work, stop scheduled polls and backfills for the moved lanes, and move the provider credentials and egress ownership to the standalone worker. Make each moved HTTP route and MCP handler a cache-only reader. `CG_ENGINE=off` and `CG_SCAN=off` stop the background entry points. Direct route fetch branches also need removal or an enforced cache-only mode. Treat `live=1`, explicit warm/backfill routes and manual tools as part of the same cutover. A cache miss returns age and coverage status or a documented unavailable response. It never starts a second upstream request.
3. Supervise one active worker with Windows Service Control Manager through a native service wrapper or an equivalent supervisor. Use bounded restart backoff, health and quota heartbeats, a single active provider-owner identity, and a stop-and-drain handoff before a replacement dials. Preserve a server-supplied cooldown across restarts or start conservatively until the prior rate window clears. Use a shared token bucket per actual quota scope, per-host breaker, bounded concurrent requests, and a canonical request key of source, instrument, venue set, window and parameters. Coalesce identical keys. Read quota headers and body error codes. Honor `Retry-After`, otherwise back off with jitter. Prioritize work by freshness deadline while reserving capacity for the long tail and limiting warm-up/backfill. Let execution quotes and protective management run on independent readers and processes.
4. Write a new immutable `latest_feature` revision when a bundle is materialized. Source timestamps come from feeds. Local receipt times come from the materializer, with no backdating. Deduplicate source sequences, and emit a failed or partial state when a required leg fails rather than silently carrying forward a value with a new timestamp. Publish a snapshot in one short transaction for related dimensions. Before a scheduled compile the scheduler should wait for the materializer’s cutoff watermark or record that the deadline was missed. Late commits can inform the next round. Across the cutover, compare actual upstream requests per minute by quota scope, freshness coverage and route failures.

### Schema and latency

| Table | Role |
| --- | --- |
| `latest_feature` | Short append-only revision ring. The composite index selects the newest received revision at or before the cutoff for each wanted key, using row ID as the tie breaker. Status and the complete normalized input are stored together. Keep the ring long enough to cover maximum round lateness, scheduler retry and local diagnostics. |
| `round` | One immutable signed envelope per round ID and nonce. Authoritative for crash recovery and export. Store the database and the report directory on a local persistent volume outside the Next build and git-sync tree. |
| `round_cell` | The immutable coverage index. One row per asset and dimension points to the hash of that cell in the envelope. A uniqueness constraint, foreign key and append-time validation protect the index. |

The compiler makes one indexed SQL extraction for 3,696 cells and the runtime record under a short WAL read transaction. Its `extraction_ms` includes the SQL, transaction and JS row materialization. Parsing, evidence checks, signing and durable publication run outside that read transaction. Seal the report and its index in a short `BEGIN IMMEDIATE` transaction. SQLite serializes this with the collector's brief writes. If the writer lock affects latency, route both mutations through a single storage writer before scaling the DB. Keep feature rows compact and put raw replies in an immutable content-addressed archive. Batch retention pruning off the deadline, preserve at least the predecessor of the oldest active cutoff, and monitor WAL size, checkpoint delay and writer lock time. Verify the SQLite runtime includes the upstream WAL-reset fix before concurrent writers. Use read-only connections for Next and MCP. Keep these three implementation files in one folder. Execute the commands relative to that folder or refer to the script by its full path. Create the DB parent directory and a protected key/output location before running.

Use a maintained Node runtime with a stable local disk driver and a pinned SQLite version. Generate an Ed25519 keypair through an operator-controlled enrollment workflow. Restrict the signing process and private key under a distinct Windows service identity and ACL, and pin the public key in the verifier and gateway. The scheduler writes an ACL-protected request containing `round_id`, a fresh random hex `nonce` of at least 128 bits, integer UTC `cutoff_ms` and `expires_ms`, and the two values from `fingerprint`. The cutoff must already have passed at compile time. Expiry may be at most 120 seconds from cutoff, and should be shorter in production. The reference verifier is for live authorization-age evidence. Historical replays need a separate offline interface with a trusted old manifest and build. Keep the signed envelope private because it contains detailed gateway provenance and account data. Render a redacted summary for other readers.

**Manifest.** Build the sorted exact asset ID list from `CURATED`, not `CG_SCAN_ASSETS` or the legacy-plus-curated scanner list. Use `policy_id = "cg-terminal/phase2-shadow-v1"`, `runtime_max_age_ms`, `btc_macro_max_age_ms`, and `assets`. Each asset contains `id`, `routes` (array of `MT5` or `DELTA`), booleans `alt`, `crypto`, `grade_b_allowed`, integer `min_wall_cents` and `max_entry_tolerance_ticks`, decimal string `tick_unit`, and `dimensions` keyed 1 through 16. Each applicable dimension has `{applies:true,max_age_ms:...,subfeeds:{sourceName: max_age_ms}}`. Supply `spot` and `perp` in D08 and `3d`, `7d`, `30d` in D11 for routable assets. Add any necessary venue legs and the stopmap wherever the approved sleeve requires it. An exception has `{applies:false,reason:"..."}`. The reference allows D13 to be exempted outside BTC/ETH and permits approved exemptions for non-routable instruments. Explicitly decide classic-instrument applicability. A required unsupported dimension holds the round incomplete. The scheduler pins the exact manifest and policy build. A count of 231 by itself cannot establish the actual universe.

**Collector rows.** Store `body = {data: normalizedFacts, subfeeds: {feedId: {state:"VALID",observed_ms,received_ms,sha256,source}}}`. Hash the archived provider evidence. The compiler checks every expected leg and effective age at cutoff. Operations must verify source identity, venue membership, sequence, units and provider permission before writing `VALID`. The compiler verifies structure and timestamps against the manifest. It cannot infer feed authenticity from a syntactically valid hash. Use explicit coverage for a valid empty response. Store shelf/wall geometry in the common instrument coordinate after basis, bin and trigger adjustments, and use **integer per-asset ticks**, **integer USD cents**, **integer UTC milliseconds**, and **basis points**. `z_bp = 10,000 × z`, `ratio_milli = 1,000 × LSR`, and RSI basis points encode the scale 0–100 as 0–10,000. Slippage ticks round outward and money losses round up. A displayed wall list without the needed covered price path cannot justify a valid empty hazard test. The top of `round_policy.mjs` is the executable field contract for D01–D16.

**Runtime row.** Put `@runtime`, dimension 0, in the same snapshot. Only the trusted materializer may ingest it, from the deterministic planner and the gateway under a local authenticated channel. `positions` covers every terminal-owned live position after broker and ticket reconciliation. `accounts` has fresh verified capacity, equity, and reservation totals for both routes in this reference. `intents` supplies structured proposals from existing DECIDE/PIT-16 logic and venue valuation receipts, never LLM-selected pass booleans. Quotes and valuations must be fresh at cutoff. The policy uses the supplied stop, target, fees-inclusive adverse valuation and declared fee-aware breakeven/time-stop prices. Producer code must bind receipts to account, instrument, side, quantity, quote/entry/stop tick, stressed exit, margin and fee inputs. Use `snapshot_sha256`, `plan_sha256`, `valuation_sha256`, and the evidence hashes specified in the module to retrieve those exact archived facts. No proposal or proof supplied by a chat or WAKE message should enter this lane.

The runtime `planner` array must match the sorted manifest asset IDs exactly. Each record carries `asset_id`, `state` (`PROPOSED`, `NO_SETUP` or `OBSERVE_ONLY`), `reason_code`, an archived `evidence_sha256`, and sorted `intent_ids`. The compiler checks that every asset is accounted for and reconciles its listed intent IDs with the actual proposals. A missing planner row or an unresolved disposition keeps the round incomplete even when all 3,696 telemetry rows are valid. The planner adapter must actually execute strategy evaluation for each routable asset before attesting its outcome.

### What executes on a compile

- Materialize exactly one row per expected key. Classify missing, stale, failed, unsupported, insufficient coverage, valid or predeclared inapplicability. Match an expected subfeed by key and enforce its independent freshness limit.
- Calculate eight Table 7 factors on an integer half-point scale. Apply eleven explicit gate decisions per proposed intent and record G05/G06 separately for the whole owned position book. Missing protection evidence yields indeterminate gates. A serialized report can contain a veto and still represent a complete audit. A missing or incomplete global audit yields no eligible intent IDs. The report is an attestation. The separate position supervisor performs exits, stop tightening and breakeven updates.
- Hash canonical JSON with SHA-256, sign the domain-separated digest with Ed25519, and commit the envelope and its indexed cells together. Publish `round_<id>.json` through an atomic, no-overwrite link on a local filesystem. A retry with the same request re-exports the original bytes after a crash. The verifier checks the pinned key and canonical signature, exact request and expiry, policy, coverage, and deterministically recomputes the outcomes from the signed evidence.
- Replay-tested signing begins at the scope of the supplied reference policy. Confirm the desk’s choices before promotion. This implementation retains the literal G02 veto for a shelf inside entry-to-stop even if PIT-16 puts the stop beyond it. It requires a 2R net minimum generally and 2.5R plus the Oracle condition for Delta Grade A, uses the strict venue/grade/heat caps, and requires the modeled exit to include at least 120% of executable stop distance plus monetary costs. It retains Table 7’s Delta-only friction point and applies an additional entry-zone limit from the manifest. It assumes the planner has checked venue tick size, position structure and sleeve prerequisites that are outside the eleven gates. Discretionary risk increases and automatic order placement are excluded. Resolve overlapping prose and test all boundaries before changing the pinned policy. ## 3. Shared-account risk admission

Use cents from the live broker, rounded conservatively. Let `E` be executable marked equity, `F = max(F_broker_daily, F_internal, F_total)`, and `O = max_s Σ_i loss_i(s)` for simultaneous account-wide scenarios. Each nonnegative `loss_i(s)` is incremental from the **current** liquidation-side mark for ticket `i` to its stressed exit in scenario `s`. Include spread changes, gaps, slippage, conversion, commission, financing, and correlated movement across all open positions. Pad the model with a separate reserve for latency, valuation uncertainty and remaining report-to-send shock. Use a complete set of pending commitments, including amendments, uncertain acknowledgments and external pending orders. Partition filled and unfilled amounts to avoid double reservation.

```text
remaining = max(0, E − max(F_broker_daily, F_internal, F_total)
                   − O − pending_reserve − shock_reserve − epsilon)
spendable = min(remaining, remaining_terminal_heat)
admit iff candidate_stressed_loss <= min(spendable, per_trade_cap, grade_cap)
```

Use a positive `epsilon` to keep stressed equity strictly above the floor. The `sharedHeadroom()` reference function in `round_policy.mjs` implements this arithmetic and rejects scenarios with missing tickets. Pending reservations cover all plausible concurrent fills. Avoid netting projected profits against stressed external losses unless a proved hedge stays executable through the same shock.

For the supplied numbers, equity minus balance is **$26.16**. A simple giveback of that floating profit costs **$26.16 from today’s marked equity**, before any adverse move through entry. The $250 loss allowance implies a $2,250 total equity floor if the plan uses a static $2,500 baseline. The $100 is an allowance; its daily floor depends on the verified reset basis and plan. For illustration, **if** the verified daily anchor were $2,551.50 and the desk used its $80 early stop, the internal floor would be $2,471.50 and gross current headroom $106.16. Giving back all floating profit would leave $80 before further scenario losses, reservations and buffers. With a hypothetical $80 stressed open loss, $15 pending, $10 shock reserve and $0.01 epsilon, that becomes **$1.15 before terminal-heat and trade caps**. The account data supplied do not establish the actual reset anchor or stressed book.

The gateway must refresh equity, verified floors, positions and pending orders immediately before admission. Freeze new risk if any input is stale, a co-located book is incomplete, a stop is missing and maximum loss is unbounded under policy, or the account resets during the calculation. For terminal requests, serialize check, reserve and outbox insert under an account-scoped transaction, then reconcile fills or uncertain send results by idempotency ID. Do not release headroom on a timeout alone. Reconcile external exposure continuously and cancel only owned unfilled orders when the modeled limit is threatened, subject to broker policy. Gaps and independent external orders can still breach the account even with a zero terminal budget. An account-wide admission controller or a separate account addresses concurrent external risk creation. Neither can guarantee a realized drawdown floor through arbitrary market gaps.
